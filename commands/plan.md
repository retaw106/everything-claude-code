# Plan 命令

此命令调用 **planner** agent 在编写任何代码之前创建全面的实现计划。

## 此命令的功能

1. **重述需求** - 阐明需要构建什么
2. **识别风险** - 表面潜在问题和阻碍因素
3. **创建分步计划** - 将实现分解为阶段
4. **等待确认** - 必须收到用户批准才能继续

## 何时使用

在以下情况下使用 `/plan`：
- 开始一个新功能
- 进行重要的架构更改
- 进行复杂的重构
- 多个文件/组件将受到影响
- 需求不清楚或模棱两可

## 工作原理

planner agent 将：

1. **分析请求** 并以清晰的术语重述需求
2. **分解为阶段** 并有具体、可操作的步骤
3. **识别依赖关系** 在组件之间
4. **评估风险** 和潜在阻碍因素
5. **估计复杂度**（高/中/低）
6. **展示计划** 并等待您的明确确认

## 使用示例

```
用户: /plan 我需要在市场结算时添加实时通知

Agent (planner):
# 实现计划：实时市场结算通知

## 需求重述
- 当用户关注的市场结算时发送通知
- 支持多种通知渠道（应用内、电子邮件、webhook）
- 确保通知可靠送达
- 包含市场结果和用户的持仓结果

## 实现阶段

### 阶段 1：数据库 Schema
- 添加 notifications 表，列包括：id, user_id, market_id, type, status, created_at
- 添加 user_notification_preferences 表用于渠道偏好
- 在 user_id 和 market_id 上创建索引以提高性能

### 阶段 2：通知服务
- 在 lib/notifications.ts 中创建通知服务
- 使用 BullMQ/Redis 实现通知队列
- 为失败投递添加重试逻辑
- 创建通知模板

### 阶段 3：集成点
- 挂钩到市场结算逻辑（当状态变为 "resolved" 时）
- 查询市场中所有持仓的用户
- 为每个用户排队通知

### 阶段 4：前端组件
- 在头部创建 NotificationBell 组件
- 添加 NotificationList 模态框
- 通过 Supabase subscriptions 实现实时更新
- 添加通知偏好设置页面

## 依赖关系
- Redis（用于队列）
- 电子邮件服务（SendGrid/Resend）
- Supabase 实时 subscriptions

## 风险
- 高：电子邮件可送达性（需要 SPF/DKIM）
- 中：每个市场 1000+ 用户时的性能
- 中：如果市场频繁结算可能导致通知垃圾信息
- 低：实时订阅开销

## 预计复杂度：中
- 后端：4-6 小时
- 前端：3-4 小时
- 测试：2-3 小时
- 总计：9-13 小时

**等待确认**：是否按此计划进行？（yes/no/modify）
```

## 重要说明

**关键**：planner agent **不会**编写任何代码，直到您用 "yes" 或 "proceed" 或类似的肯定回复明确确认计划。

如果您想要更改，请回复：
- "modify: [您的更改]"
- "different approach: [替代方案]"
- "skip phase 2 and do phase 3 first"

## 与其他命令的集成

计划之后：
- 使用 `/tdd` 进行测试驱动开发实现
- 如果发生构建错误，使用 `/build-fix`
- 使用 `/code-review` 审查完成的实现
