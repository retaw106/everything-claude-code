# /learn-eval - 提取、评估、然后保存

扩展 `/learn`，增加了质量门、保存位置决策和知识放置感知，在写入任何 skill 文件之前。

## 提取什么

寻找：

1. **错误解决模式** — 根本原因 + 修复 + 可重用性
2. **调试技术** — 非显而易见的步骤、工具组合
3. **变通方案** — 库怪癖、API 限制、版本特定修复
4. **项目特定模式** — 约定、架构决策、集成模式

## 流程

1. 审查会话以提取可提取的模式
2. 识别最有价值/可重用的洞察

3. **确定保存位置：**
   - 问："这个模式在不同项目中有用吗？"
   - **全局**（`~/.claude/skills/learned/`）：可在 2+ 项目中使用的通用模式（bash 兼容性、LLM API 行为、调试技术等）
   - **项目**（当前项目中的 `.claude/skills/learned/`）：项目特定知识（特定配置文件的怪癖、项目特定的架构决策等）
   - 有疑问时，选择全局（全局 → 项目比反向更容易）

4. 使用此格式起草 skill 文件：

```markdown
---
name: pattern-name
description: "130 字符以内"
user-invocable: false
origin: auto-extracted
---

# [描述性模式名称]

**提取时间：** [日期]
**上下文：** [适用场景的简要描述]

## 问题
[这解决什么问题 - 要具体]

## 解决方案
[模式/技术/变通方案 - 带代码示例]

## 何时使用
[触发条件]
```

5. **质量门 — 检查清单 + 整体评估**

   ### 5a. 必需检查清单（通过实际读取文件验证）

   在评估草稿前执行**所有**以下操作：

   - [ ] 通过关键字 Grep `~/.claude/skills/` 和相关项目 `.claude/skills/` 文件以检查内容重叠
   - [ ] 检查 MEMORY.md（项目和全局）是否有重叠
   - [ ] 考虑追加到现有 skill 是否足够
   - [ ] 确认这是可重用模式，而非一次性修复

   ### 5b. 整体评估

   综合检查清单结果和草稿质量，然后选择**以下之一**：

   | 评估 | 含义 | 下一步操作 |
   |------|------|------------|
   | **保存** | 独特、具体、范围明确 | 继续步骤 6 |
   | **改进后保存** | 有价值但需要改进 | 列出改进 → 修订 → 重新评估（一次） |
   | **吸收到 [X]** | 应追加到现有 skill | 展示目标 skill 和添加内容 → 步骤 6 |
   | **放弃** | 微不足道、冗余或太抽象 | 解释原因并停止 |

   **指南维度**（影响评估，不打分）：

   - **具体性和可操作性**：包含立即可用的代码示例或命令
   - **范围适配**：名称、触发条件和内容对齐并专注于单个模式
   - **独特性**：提供现有 skills 未覆盖的价值（由检查清单结果告知）
   - **可重用性**：未来会话中存在现实的触发场景

6. **评估特定的确认流程**

   - **改进后保存**：展示所需的改进 + 修订后的草稿 + 一次重新评估后更新的检查清单/评估；如果修订后的评估是**保存**，在用户确认后保存，否则遵循新评估
   - **保存**：展示保存路径 + 检查清单结果 + 1 行评估理由 + 完整草稿 → 用户确认后保存
   - **吸收到 [X]**：展示目标路径 + 添加内容（diff 格式）+ 检查清单结果 + 评估理由 → 用户确认后追加
   - **放弃**：仅展示检查清单结果 + 理由（无需确认）

7. 保存/吸收到确定的位置

## 步骤 5 的输出格式

```
### 检查清单
- [x] skills/ grep：无重叠（或：发现重叠 → 详情）
- [x] MEMORY.md：无重叠（或：发现重叠 → 详情）
- [x] 现有 skill 追加：新文件适当（或：应追加到 [X]）
- [x] 可重用性：已确认（或：一次性 → 放弃）

### 评估：保存 / 改进后保存 / 吸收到 [X] / 放弃

**理由：**（1-2 句解释评估）
```

## 设计理由

此版本用基于检查清单的整体评估系统替换了之前的 5 维度数字评分标准（具体性、可操作性、范围适配、非冗余性、覆盖率得分 1-5）。现代前沿模型（Opus 4.6+）具有强大的上下文判断能力 —— 将丰富的定性信号强制转换为数字分数会失去细微差别，并可能产生误导性总分。整体方法让模型自然权衡所有因素，产生更准确的保存/放弃决策，而显式检查清单确保不会跳过关键检查。

## 注意事项

- 不要提取微不足道的修复（拼写错误、简单的语法错误）
- 不要提取一次性问题（特定的 API 中断等）
- 关注能节省未来会话时间的模式
- 保持 skills 专注 — 每个模式一个 skill
- 当评估为吸收时，追加到现有 skill 而非创建新文件
