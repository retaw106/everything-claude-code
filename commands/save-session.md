# Save Session 命令

捕获本次会话中发生的一切 — 构建了什么、什么有效、什么失败、剩下什么 — 并将其写入带日期的文件，以便下次会话可以准确地从中断处继续。

## 何时使用

- 在关闭 Claude Code 之前的工作会话结束时
- 在达到上下文限制之前（先运行此命令，然后开始新会话）
- 在解决了一个你想记住的复杂问题后
- 任何时候你需要将上下文移交给未来的会话

## 流程

### 步骤 1：收集上下文

在写入文件之前，收集：

- 读取本次会话期间修改的所有文件（使用 git diff 或从对话中回忆）
- 审查讨论、尝试和决定的内容
- 注明遇到的任何错误及其解决方式（或未解决）
- 如果相关，检查当前测试/构建状态

### 步骤 2：创建 sessions 文件夹（如果不存在）

在用户的 Claude 主目录中创建规范的 sessions 文件夹：

```bash
mkdir -p ~/.claude/session-data
```

### 步骤 3：写入会话文件

创建 `~/.claude/session-data/YYYY-MM-DD-<short-id>-session.tmp`，使用今天的实际日期和一个满足 `session-manager.js` 中 `SESSION_FILENAME_REGEX` 强制规则的 short-id：

- 兼容字符：字母 `a-z` / `A-Z`、数字 `0-9`、连字符 `-`、下划线 `_`
- 兼容最小长度：1 个字符
- 新文件推荐风格：小写字母、数字和连字符，8+ 字符以避免冲突

有效示例：`abc123de`、`a1b2c3d4`、`frontend-worktree-1`、`ChezMoi_2`
新文件避免：`A`、`test_id1`、`ABC123de`

完整有效文件名示例：`2024-01-15-abc123de-session.tmp`

Legacy 文件名 `YYYY-MM-DD-session.tmp` 仍然有效，但新会话文件应优先使用 short-id 形式以避免同日冲突。

### 步骤 4：用下面的所有部分填充文件

诚实地写入每个部分。不要跳过部分 — 如果某个部分确实没有内容，写入"尚无"或"不适用"。不完整的文件比诚实的空部分更糟糕。

### 步骤 5：向用户展示文件

写入后，显示完整内容并询问：

```
会话已保存到 [会话文件的实际解析路径]

这看起来准确吗？在关闭前有什么要修正或添加的吗？
```

等待确认。如果请求则进行编辑。

## 示例输出

```markdown
# Session: 2024-01-15

**开始时间：** ~下午2点
**最后更新：** 下午5:30
**项目：** my-app
**主题：** 使用 httpOnly cookies 构建 JWT 认证

---

## 我们在构建什么

Next.js 应用的用户认证系统。用户使用 email/password 注册，
收到存储在 httpOnly cookie（而非 localStorage）中的 JWT，受保护的路由
通过 middleware 检查有效的 token。目标是跨浏览器刷新的会话持久化
而不将 token 暴露给 JavaScript。

---

## 什么有效（带证据）

- **`/api/auth/register` 端点** — 确认方式：Postman POST 返回 200 并带有用户
  对象，在 Supabase 仪表板中可见行，bcrypt hash 正确存储
- **`lib/auth.ts` 中的 JWT 生成** — 确认方式：单元测试通过
  （`npm test -- auth.test.ts`），在 jwt.io 解码 token 显示正确的 payload
- **密码哈希** — 确认方式：测试中 `bcrypt.compare()` 返回 true

---

## 什么无效（以及原因）

- **Next-Auth 库** — 失败原因：与我们的自定义 Prisma adapter 冲突，
  每次请求都抛出"Cannot use adapter with credentials provider in this configuration"。
  不值得调试 — 对我们的设置太固执己见。
- **在 localStorage 中存储 JWT** — 失败原因：SSR 渲染发生在
  localStorage 可用之前，每次页面加载都导致 React hydration 不匹配错误。
  这种方法与 Next.js SSR 根本不兼容。

---

## 尚未尝试的方法

- 在登录路由响应中将 JWT 存储为 httpOnly cookie（最可能的解决方案）
- 使用 `next/headers` 中的 `cookies()` 在服务器组件中读取 token
- 编写 middleware.ts 通过检查 cookie 存在来保护路由

## 做出的决定

- **httpOnly cookie 而非 localStorage** — 原因：防止 XSS token 窃取，与 SSR 兼容
- **自定义 auth 而非 Next-Auth** — 原因：Next-Auth 与我们的 Prisma 设置冲突，不值得纠缠
```

## 注意事项

- 每个会话有自己的文件 — 永远不要追加到之前会话的文件
- "什么无效"部分是最关键的 — 没有它，未来的会话会盲目地重试失败的方法
- 如果用户要求在会话中期保存（不仅仅是在结束时），保存已知内容并清楚地标记进行中的项目
- 文件旨在在下次会话开始时通过 `/resume-session` 由 Claude 读取
- 使用规范的全局会话存储：`~/.claude/session-data/`
- 对于任何新会话文件，优先使用 short-id 文件名形式（`YYYY-MM-DD-<short-id>-session.tmp`）
